# Приёмка по ПМИ: план

Источник — «ПМИ ARQA-1, Приложение А. Контрольные примеры» (таблица А.1, А-1…А-25).
Самого ТЗ в репозитории нет, поэтому пункты со ссылками на него (4.1.2.4, 4.1.6.2, 4.1.7.2,
4.8.1.1, таблица 2, раздел 6.2) проверяются только в той части, которая видна из ПМИ.

Ветка: `feat/pmi-acceptance` от `develop`, без пушей.

## Что получится

1. `tests/acceptance/` — автотесты по контрольным примерам, по файлу на пример
   (`test_a01_….py` … `test_a25_….py`). В docstring каждого теста — шаги и ожидаемый
   результат из ПМИ.
2. `docs/pmi-report.md` — отчёт: что готово, что частично, чего нет, с доказательством
   (какой тест, какой прогон).
3. README: корневой — что это за система и как она работает в целом; в пакетах — как
   пользоваться конкретным пакетом. У `openapi-parser` README нет — написать.

## Как устроены приёмочные тесты

Тесты проверяют систему целиком, через её настоящие входы: CLI `arqa-testgen`, HTTP API
testing_tools, демо-сервисы из `demo/`.

| Что нужно тесту        | Чем обеспечивается                                                        |
|------------------------|---------------------------------------------------------------------------|
| LLM                    | по умолчанию — локальный сценарный OpenAI-совместимый сервер (как в тестах агента): отвечает по сценарию и записывает, что ему прислали |
| Настоящая LLM          | маркер `llm`: тест запускается, только если заданы `DEEPCODE_*` и `ARQA_LLM_TESTS=1` |
| Демо-сервисы           | `demo/petstore`, `demo/orders` поднимаются в процессе теста (uvicorn в потоке) |
| testing_tools          | `create_app(Settings(...))` в потоке uvicorn, результаты — во временный каталог |
| Microcks               | маркер `docker`: нужен запущенный Microcks (`ARQA_MICROCKS_URL`)          |

Если функции в системе нет, тест всё равно пишется по ожидаемому результату ПМИ и
помечается `xfail(strict=True, reason=...)`. Он виден в отчёте pytest как известный
пробел и сам «покраснеет», когда функцию допишут и маркер станет лишним.

Запуск:

```bash
uv run pytest tests/acceptance                 # офлайн: без ключа и Docker
ARQA_LLM_TESTS=1 uv run pytest tests/acceptance -m llm   # с настоящей моделью из .env
```

## Найденные проблемы интеграции (чинить или нет — решает пользователь)

- Агент предлагает модели `evomaster`, а testing_tools в develop его не знает (`ToolName`
  без EvoMaster, сервер остался в `WiP/testing-tools`) → вызов вернёт 422.
- Агент не умеет передать в testing_tools свои тесты (инструмент `mutation`): gateway шлёт
  только schemathesis/microcks/evomaster.
- `backend/testing_tools/.python-version` = 3.14, а workspace и venv на 3.13: `uv run` из
  каталога пакета может пересоздать общий `.venv` под 3.14.
- `pytest backend/testing_tools` из корня собирает `examples/sample_agent_tests` (им нужен
  живой сервис) → 17 ошибок. Из каталога пакета всё зелёное.
- CI не запускает тесты и mypy testing_tools.
- Корневой `pyproject.toml` зависит только от `agent`; `testing-tools` ставится лишь с
  `--all-packages`.
